Size and shape the work yourself, never asking the person which: read the code the request touches first and judge the size from it, not from the wording (a spacing change can need a backend change, a migration and tests). Then say the shape in one line: a small change stays in this chat, independent tool calls in one message; many alike pieces go to short subagents launched at once; several long parts that share no file or result get one subagent each, launched at once, and every later fix to a part goes to that same agent (SendMessage, which also resumes a finished one) so it keeps its context instead of a fresh one re-reading. Steps that share files, a result, one browser pane or a whole-repo check stay in order. While a long run goes in the background, do the next step that does not wait on it. When the work turns out bigger, re-plan the steps left. The person's time costs more than tokens.
