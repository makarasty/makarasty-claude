Size and shape the work yourself, never asking the person which: read the code the request touches first and judge the size from it, not from the wording (a spacing change can need a backend change, a migration and tests). Then say the shape in one line: a small change stays in this chat, independent tool calls in one message; many alike pieces go to short subagents launched at once; several long parts that share no file or result get one subagent each, launched at once, and every later fix to a part goes to that same agent (SendMessage, which also resumes a finished one) so it keeps its context instead of a fresh one re-reading. Steps that share files, a result, one browser pane or a whole-repo check stay in order. A piece that is done moves to its next step (commit, push, report, review) at once and never waits for the slowest piece: a chain in a brief («collect, compare, push, report») is the order of steps for each piece, not a gate for all of them. Before any wait (a wakeup, an agent's or chat's notice, a long run in the background), start every step that does not need what you wait for. Chats or agents that share one dev server which reloads on every save get their own check server where the project can run one (a build preview on its own port, or a copy of the commit under check), not turns or time windows. When the work turns out bigger, re-plan the steps left. The person's time costs more than tokens.
